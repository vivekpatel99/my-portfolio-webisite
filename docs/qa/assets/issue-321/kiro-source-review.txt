## Findings

### 1. Medium: a "Submission Failed" toast can survive a remount and appear next to the receipt
`src/pages/Contact.jsx:69, 140–141, 161`

- **Cause:** `feedbackToastRef` belongs to each component instance. When a send is still pending and Contact unmounts, the old instance's `handleSubmit` keeps running after the `await`. Its toast handle is saved in the old, unmounted instance's ref (line 161).
- **Effect:** after the user returns, the new instance's ref is `null`, so `feedbackToastRef.current?.dismiss()` at line 140 does nothing on retry. The failure toast lasts 5 seconds (`use-toast.js`, `duration || 5000`), so a quick retry that succeeds shows the receipt and "Submission Failed" together.
- **Existing coverage:** issue #230 tests dismissal only within one instance. `'#265: pending failure after navigation…'` doesn't check dismissal.
- **Acceptance criteria:**
  - Unit test: start a pending submit, unmount, reject, remount, retry, and assert the failure handle's `dismiss` is called exactly once.
  - Lifecycle spec: in the "failure completed away" case, retry within 5 seconds of returning. Expect zero failure toasts and one receipt.
- **Likely fix:** keep the toast handle in the module store next to `submission`/`outcome`, or dismiss it inside `beginSubmission`.

### 2. Medium: the saved outcome takes focus and scroll on every later visit to Contact
`src/pages/Contact.jsx:73–76` with `src/lib/useContactDraft.js:7, 55`

- **Cause:** `outcome` stays in the store until a field is edited. Contact's `useEffect(..., [outcome])` runs on every mount.
- **Effect:** every later visit puts focus on the receipt (or the retry button) and scrolls to it. That includes a fresh header-CTA visit (PUSH) minutes later, and it overrides `ScrollToTop`'s scroll-to-top and focus on main. The receipt is `role="status"` and is re-inserted each time, which may also re-announce it.
- **Spec gap:** `docs/qa/contact-remount-321.md` says the receipt "focuses … after returning" but doesn't say whether that applies once or on every visit. `returnToContactByBack` currently accepts focus on the receipt for any return.
- **Acceptance criteria:** decide and test the rule. My suggestion: focus the outcome at most once per completion (for example, a `presented` flag in the store). For later visits, assert focus on `#main-content` and `scrollY === 0`, while the receipt remains visible.

### 3. Low: the router's focus guard depends on Contact's DOM
`src/components/ScrollToTop.jsx:24`

- **What happens:** the generic route component checks a Contact-specific attribute for every path, without checking `pathname`.
- **Today:** this is safe. `App.jsx` has no `AnimatePresence`, so the old route unmounts when navigation commits and the outcome element is already detached by the time the frame runs.
- **Risk:** if exit animations are added later (the existing test "moves focus off a source action still mounted…" expects that), a focused receipt during browser Back would stop main from receiving focus on the destination route.
- **Missing coverage:** no unit test in `ScrollToTop.test.jsx`, either positive or negative.
- **Acceptance criteria:** add both cases to `ScrollToTop.test.jsx`, and ideally scope the guard to the destination path.

### 4. Low: a successful send can show no feedback if the draft changed
`src/lib/useContactDraft.js:48–58`

If `formState` changes while a send is pending, a success sets `outcome: null` and shows no toast. The user never learns the send succeeded. The UI can't trigger this today because the fields are disabled while submitting. The existing test (`'does not let a stale completion…'`) treats this silence as intended. Either accept that explicitly or show some outcome.
